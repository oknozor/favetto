# Agent guide

This is the canonical guide for AI coding agents — and new contributors —
working in `oknozor/favetto`. It records the checks that must pass **before you
push** and the commit rules that are enforced on every push and pull request.
The same rules also live in `.github/workflows/ci.yml`, `cog.toml`, the README's
[Checks](README.md#checks) section, and the
[releasing guide](docs/guide/releasing.md); this file is the single place to read
first.

## Pre-push gates

Run these from the workspace root. They match CI exactly and must all pass before
you push.

```bash
cargo fmt --all -- --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo nextest run --locked --workspace   # install: cargo install cargo-nextest
```

The generated reference is also checked by CI and must not drift. Regenerate it,
then fail if the committed output changed:

```bash
cargo run --locked -p favetto -- __doc
git diff --exit-code -- docs/reference docs/public/favetto-schema.json
```

The documentation site build is the last gate; it fails on dead internal links:

```bash
cd docs && npm ci && npm run docs:check
```

> While iterating you can run a single gate on its own, but run the full workspace
> commands above before you finish. CI uses `--locked` everywhere, so keep
> `Cargo.lock` in sync.

## Commit conventions (mandatory)

History must follow [Conventional Commits](https://www.conventionalcommits.org/).
cocogitto derives the next version from the commits since the last tag, and CI
enforces the format on every push and pull request.

Install the shareable commit-msg hook once per clone (hooks under `.git/hooks`
are not versioned):

```bash
cog install-hook --all
```

The hook runs `cog verify` on the message and `cog check` over the history, then
the formatting and lint gates from above. You can run them by hand at any time:

```bash
cog verify --file <message-file>   # a single commit message
cog check                          # the whole history
cog changelog                      # preview the unreleased changelog
```

### Bump table

| Commit | Bump |
|--------|------|
| `fix:` | patch (`0.1.0` → `0.1.1`) |
| `feat:` | minor (`0.1.0` → `0.2.0`) |
| `feat!:` / `BREAKING CHANGE:` | major (`0.1.0` → `1.0.0`) |

`chore:` and `test:` commits are kept out of the changelog, and merge commits are
ignored. Only `main` receives version bumps (`branch_whitelist = ["main"]` in
`cog.toml`), and the version is never edited by hand — it lives in
`[workspace.package] version` and is written during a release.

## Workspace and toolchain

- Workspace members:
  - `crates/favetto-core` — shared wire protocol, domain types, and pure shared
    modules (config, tasks, workflow, template, paths, ws); no HTTP/DB/LLM.
  - `crates/favetto-providers` — provider/model catalog (opencode auth + models.dev).
  - `crates/favetto` — the daemon and doc generator; its `tui` subcommand is a
    thin dispatcher that execs `favetto-tui`.
  - `crates/favetto-tui` — the standalone ratatui client binary. It links only
    the client dependency tree (no axum/sqlx/portable-pty/tokio-cron-scheduler/notify).
- Rust edition 2021, `rust-version = 1.92`, workspace resolver `2`.
- Tests are inline `#[cfg(test)]` modules next to the code they cover, often
  using `#[tokio::test]`; add cases there.
- Tasks live in `tasks/` — `*.md` files with a TOML header followed by the prompt.
- Documentation is a VitePress site under `docs/`; the reference pages are
  generated by `cargo run -p favetto -- __doc`.

Keep changes focused on the affected crate and do not refactor unrelated code.
`.favetto/` (plans, handoffs, triage reports) is gitignored and must not be
committed.
